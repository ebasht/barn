# Barn DB Migration

Use this workflow for PostgreSQL schema/data migrations or changes to `backend/queries/*.sql` and sqlc output.

## Inspect before changing

Read `AGENTS.md` and `backend/AGENTS.md`. Then identify the table, all migrations that formed it, its complete definition in `backend/schema/schema.sql`, named queries in `backend/queries/`, generated consumers in `backend/internal/db/`, domain services, API DTOs, and frontend fields:

```sh
rg -n 'table_name|column_name|QueryName' backend/migrations backend/schema backend/queries backend/internal --glob '!backend/internal/db/*.go'
rg -n 'QueryName|GoField|json_field' backend/internal frontend docs
```

Inspect generated files only to understand impact. A generated header, rather than the directory alone, determines whether a file is generated; for example, `internal/db/mcp_logs.go` is maintained by hand.

## Create the migration

1. Determine the largest committed `backend/migrations/NNNNN_*.sql` number and add the next zero-padded number with a descriptive snake-case name. Never reuse a number or modify an already released migration; git tags/releases determine whether it has shipped.
2. Include `-- +goose Up` and a truthful `-- +goose Down`. If reversal would destroy data or cannot be made safe, do not pretend it is lossless: use the least-surprising explicit down behavior and call out the limitation.
3. Make upgrades safe for populated installations. Consider defaults/backfill ordering, nullability, uniqueness conflicts, lock duration, referential actions, existing Barn/DockPilot names, and whether application code must tolerate old and new states during rollout.
4. For data migrations, make the target set deterministic and avoid silently discarding ambiguous data. Keep SQL in goose `StatementBegin/StatementEnd` when the construct requires it.
5. Apply the resulting final schema to `backend/schema/schema.sql`. This file is sqlc's canonical schema input; running goose does not update it.

## Queries and generation

- Put named queries in the matching `backend/queries/*.sql` using sqlc's `-- name: QueryName :one|:many|:exec` convention.
- Prefer explicit columns and stable ordering where API behavior depends on order. Check nullable/default types and row cardinality.
- From `backend/`, run `sqlc generate`. Do not hand-edit files whose header says `Code generated by sqlc`.
- Review the generated diff. Update services, mappers, DTOs, handlers, tests, and frontend contracts for changed Go types or JSON semantics.
- If sqlc is unavailable, do not fabricate generated code. Report the missing tool and leave generation clearly outstanding.

## Safe verification

```sh
cd backend
sqlc generate
gofmt -w <changed-non-generated-go-files>
go test ./internal/<changed-domain>
# For cross-domain/schema contract changes:
go test ./...

cd ..
git diff --check
git diff -- backend/migrations backend/schema/schema.sql backend/queries backend/internal/db
```

Check explicitly that:

- a new migration exists and prior migrations are unchanged;
- `Up` reaches the same schema represented by `schema/schema.sql`;
- `Down` syntax and data-loss characteristics are understood;
- constraints and indexes have intentional names and behavior;
- sqlc output was regenerated, not manually patched;
- API/frontend consumers and compatibility paths were updated where needed.

`make migrate` and `scripts/barn-migrate.sh` mutate a real development database and require Docker. Run them only when the user wants integration validation and the target database is confirmed disposable or backed up. Never use `make reset`, reset/recovery scripts, or volume deletion merely to test a migration.
